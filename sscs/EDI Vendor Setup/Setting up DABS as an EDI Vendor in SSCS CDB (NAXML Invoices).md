# **Setting up DABS as an EDI Vendor in SSCS CDB (NAXML Invoices)**

## **1\. Vendor Master Configuration in CDB**

Begin by adding DABS as a vendor in the Computerized Daily Book (CDB) and entering all required identification details:

* **Vendor Record:** Create a new vendor record for DABS (via the Vendor Maintenance screen in CDB). Ensure the vendor’s basic info (name, address, etc.) is entered. SSCS documentation emphasizes that you must set up the vendor in CDB first before enabling any EDI features[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=Vendor%20Import%20Setup%20Important%20Vendor,up%20your%20vendor%20records%20there).

* **DUNS Number:** Input the vendor’s DUNS (Data Universal Numbering System) identifier if available. DABS has provided a DUNS of **943556183**, which should be recorded in the appropriate field (often labeled “DUNS” or “EDI ID” in the vendor record). This unique ID helps the system recognize the trading partner in EDI transactions[blog.sscsinc.com](https://blog.sscsinc.com/2015/05/07/2015-conexxus-conf/#:~:text=SSCS%E2%80%99s%20involvement%20to%20date%20has,SSCS%20is%20an%20inaugural%20member). (SSCS’s EDI module is designed to use standard identifiers like DUNS/GLNs for matching partners, as it adheres to NAXML/Conexxus standards[blog.sscsinc.com](https://blog.sscsinc.com/2015/05/07/2015-conexxus-conf/#:~:text=SSCS%E2%80%99s%20involvement%20to%20date%20has,SSCS%20is%20an%20inaugural%20member).)

* **Store/Account Number:** Record your account or store number with DABS (e.g. **50076**) in the vendor’s details. Many EDI integrations use an account number to identify the retailer. In CDB, this might be an “Account \#” field or a “Store ID” field within the vendor profile. This value should match what DABS uses to denote your business in their invoices. Ensuring the correct account/store number is in place will allow the CDB to associate incoming files with this vendor.

* **EDI Flags/Settings:** If the CDB vendor setup has an option to mark the vendor as an **EDI vendor** or to specify an **EDI format**, enable those. For example, some systems have a checkbox or dropdown indicating the vendor will use electronic invoices. Setting this prepares the CDB to expect electronic invoice data for DABS[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=Vendor%20Import%20Setup%20Important%20Vendor,up%20your%20vendor%20records%20there). (In some configurations, the specific EDI parameters may be configured on a separate screen – see next section – but double-check if any basic flags exist in the vendor record itself.)

**Note:** At this stage, you are simply establishing DABS as a known vendor in your system with the correct identifiers. This foundational step is critical because **the EDI import process will reference the Vendor ID and data in CDB** – if the vendor isn’t set up or the IDs don’t match, the invoice file won’t be recognized[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=Vendor%20Import%20Setup%20Important%20Vendor,up%20your%20vendor%20records%20there).

## **2\. EDI Setup – Linking Vendor to NAXML Format and File Location**

With the vendor record in place, configure the EDI settings that enable automated invoice processing:

* **Access the EDI Configuration:** In CDB’s menus, navigate to the **Direct Store Deliveries / EDI Setup** screen (or similar; the exact navigation may vary by CDB version). This is where you define how the system handles incoming electronic invoices. Often it’s under a “Setup” or “Interfaces” menu related to vendors or deliveries.

* **Select the Vendor and Format:** Within the EDI setup, choose the DABS vendor you created and specify the **invoice format** it will use. DABS sends invoices in **NAXML (XML)** format, which SSCS supports as part of its standard EDI vendor formats[blog.sscsinc.com](https://blog.sscsinc.com/2015/05/07/2015-conexxus-conf/#:~:text=SSCS%E2%80%99s%20involvement%20to%20date%20has,SSCS%20is%20an%20inaugural%20member). Look for an option that corresponds to “NAXML Invoice” or a similar XML-based format. For example, SSCS documentation shows supported formats like *“McLane NAXML”* (for item/pricing files) among others[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=Vendor%20Format%20AJ%20Silberman%20and,PDI%207500%20McLane%20NAXML%20ItemSynch%2FItemPrice) – in your case, select the generic NAXML invoice schema if available. This tells CDB how to interpret the file structure. *(SSCS has been using NAXML standards for many years, so its software can parse XML invoices from suppliers in the standardized format[blog.sscsinc.com](https://blog.sscsinc.com/2015/05/07/2015-conexxus-conf/#:~:text=SSCS%E2%80%99s%20involvement%20to%20date%20has,SSCS%20is%20an%20inaugural%20member).)*

* **Specify NAXML Version (if required):** If the setup asks for a version or schema, ensure it aligns with **NAXML 1.5** (the version DABS is using). In most cases, the CDB’s “NAXML” format option will cover version 1.5, as NAXML v1.x schemas are part of the industry standards that SSCS implements[blog.sscsinc.com](https://blog.sscsinc.com/2015/05/07/2015-conexxus-conf/#:~:text=SSCS%E2%80%99s%20involvement%20to%20date%20has,SSCS%20is%20an%20inaugural%20member). There is usually no need for a custom map unless DABS has deviations from the standard. (SSCS is an active Conexxus/PCATS member, so their system is kept compatible with official NAXML invoice schemas[blog.sscsinc.com](https://blog.sscsinc.com/2015/05/07/2015-conexxus-conf/#:~:text=SSCS%E2%80%99s%20involvement%20to%20date%20has,SSCS%20is%20an%20inaugural%20member).) It’s a good practice to confirm with SSCS support that *no special patch or mapping* is needed for NAXML 1.5 – but generally, selecting the NAXML invoice format in the UI is sufficient to support that version.

* **File Location (EDI Directory):** Configure where the system will **look for incoming invoice files**. By default, SSCS’s CDB uses a designated “EDI” folder in the CDB data directory for each site. According to SSCS’s documentation, *“EDI files… are delivered to your system’s EDI folder to a specific site sub-directory”*[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=File%20Location%20%E2%80%94%20Like%20EDI,of%20importing%20you%20may%20encounter). For example, if your store is site \#001 in the system, the folder might be:

   **`Q:\cdbdata\edi\001\`** (for site 001’s EDI files)[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=File%20Location%20%E2%80%94%20Like%20EDI,of%20importing%20you%20may%20encounter).

   Ensure that the EDI setup for DABS is pointed to the correct site’s EDI folder. In many cases, this is pre-configured by site number – you may just need to verify the site is set to your store’s ID in that EDI setup screen. The SSCS Central Price Book guide explicitly notes that vendor electronic files go into the site’s EDI subdirectory for processing[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=File%20Location%20%E2%80%94%20Like%20EDI,of%20importing%20you%20may%20encounter).

   Additionally, confirm the **archive/backup path**. Typically, after CDB processes an EDI invoice file, it will move the file to a subfolder (often named **“BAK”** or “Processed”) within the same directory. For instance, once an invoice in `Q:\cdbdata\edi\001\` is processed, it might relocate to `Q:\cdbdata\edi\001\BAK\` automatically. This ensures each file is imported only once and is saved for audit purposes. (You generally do **not** need to configure the BAK folder manually – CDB handles it – but be aware of its role.)

* **File Naming and Mask:** Set up the **file mask or naming pattern** expected for DABS invoice files. If DABS emails you XML files (likely with an `.xml` extension), you can use a wildcard to capture them. For example, configure the file mask as `*.xml` to have CDB import any XML file dropped in the EDI folder[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=folder%20to%20which%20you%20wish,a%20file%20mask%20here%20such). This is useful if the system’s EDI importer filters files by type. SSCS allows wildcards for flexible matching – e.g., a mask like `*INV*.xml` could be used if all invoice files contain “INV” in the name, but generally `*.xml` is broad and safe for XML invoices[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=more%20than%20one%20type%20of,process%20a%20file%20with%20any).

   Make sure the file naming convention DABS uses (perhaps something like `Invoice_<Store>_<Date>.xml`) is accounted for. If DABS provides a specific file prefix or pattern, input that in the mask to target their files. Otherwise, a general XML mask will suffice since presumably only DABS (and possibly other EDI vendors) will be placing files in that folder.

* **Vendor Identifier/Zone (if applicable):** Some EDI setups in SSCS have a field for a *“Vendor Zone”* or ID which links the incoming file’s internal codes to the vendor[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=can%20have%20more%20than%20one,the%20vendor%20file%20to%20be). For example, a vendor might include a specific code in the XML (like a supplier ID or zone name). If DABS provided any such identifier (sometimes called a “trading partner ID” or similar), enter it in the configuration. This value helps the system route the file to the correct vendor if multiple vendors use similar formats. (In many cases, this may not be needed if the file itself clearly identifies the vendor by DUNS or if you’re only setting up one vendor for NAXML. But the field is there for multi-vendor scenarios – e.g., a central system importing for many stores/vendors – to distinguish files.)

* **Save the EDI Setup:** Once the vendor, format, path, and mask are set for DABS, save/apply the configuration. At this point, the CDB knows that **vendor DABS \= expect NAXML invoices** arriving as files in the specified directory. The system’s EDI service will monitor that folder for incoming files.

**Tip:** SSCS’s cloud customers often use an **Edidelivery service** – for example, vendors email invoice files which get automatically dropped into the EDI folder. The SSCS vendor documentation mentions that if a vendor sends files via email or OneDrive, you might need to forward those to your special `edidelivery.com` address to get them into the system[sscsinc.com](https://www.sscsinc.com/vendors/#:~:text=Vendor%20Details%20ABL%20Wholesale%20Distributors,mail%20address). Confirm with SSCS if you have an edidelivery email set up for your site. In practice, for DABS you might either save the email attachment to `Q:\cdbdata\edi\001\` manually or have it forwarded to the automated service. Once the file is in that folder, CDB will handle it from there.

## **3\. NAXML 1.5 Support and Mapping Considerations**

One of your concerns is ensuring the system correctly interprets the **NAXML 1.5** invoice format that DABS uses. Here’s what to verify:

* **Standard Schema Compliance:** SSCS CDB’s EDI module is built to handle **NAXML invoice files** as part of the industry-standard EB2B (Electronic B2B) formats[blog.sscsinc.com](https://blog.sscsinc.com/2015/05/07/2015-conexxus-conf/#:~:text=SSCS%E2%80%99s%20involvement%20to%20date%20has,SSCS%20is%20an%20inaugural%20member). In fact, SSCS was an early adopter of NAXML for invoices and purchase orders, using it in the field since 1999[blog.sscsinc.com](https://blog.sscsinc.com/2015/05/07/2015-conexxus-conf/#:~:text=SSCS%E2%80%99s%20involvement%20to%20date%20has,SSCS%20is%20an%20inaugural%20member). This means that if DABS’s files truly adhere to the NAXML 1.5 schema defined by Conexxus/NACS, the CDB should be able to parse them without issue using the generic NAXML setting. No additional “mapping file” is usually required for standard formats – SSCS maintains support for all the major vendor invoice standards through its Approved EDI Vendors program and Conexxus compliance. In short, **NAXML 1.5 is within the scope of CDB’s supported formats** by default[blog.sscsinc.com](https://blog.sscsinc.com/2015/05/07/2015-conexxus-conf/#:~:text=SSCS%E2%80%99s%20involvement%20to%20date%20has,SSCS%20is%20an%20inaugural%20member).

* **Verify Schema Version:** NAXML has evolved (later versions were often labeled under the Conexxus schema, but still backward compatible in many respects). If possible, confirm the **root element or schema reference** in the DABS XML file (e.g., it might reference a DTD/XSD with version 1.5). If the CDB’s parser encounters an unknown XML structure, it will log an error – but given SSCS’s involvement in Conexxus, this is unlikely for a standard v1.5 invoice. There is no toggle for “1.5 vs 3.4” usually – just “NAXML Invoice” – the system handles the specifics internally.

* **Custom Fields or Extensions:** If DABS included any non-standard fields in their NAXML (some trading partners add custom tags or data), those might be ignored or could potentially trip up the importer if completely unexpected. Check SSCS’s release notes or knowledge base if any special update was needed for **Utah DABS** specifically. Since DABS is a new addition, SSCS might have issued guidance if, for example, *“DABS NAXML files require patch X or mapping Y.”* In absence of such notes, assume standard handling. (The list of *Approved EDI Vendors* on SSCS’s site does not yet list DABS by name, meaning DABS may not require anything unique beyond the normal NAXML handling, or it is still considered a generic XML vendor.)

* **Testing for Mapping Accuracy:** The ultimate test of NAXML 1.5 support is to run a **sample invoice** through (see testing steps below) and verify that all data lands in the right place in CDB (items, quantities, costs, taxes, etc.). If you notice any field not populating (for instance, maybe a field like **invoice date** or **invoice number** not coming through), that could indicate a mapping issue – at which point you’d involve SSCS support to adjust the import template. However, such issues are uncommon when using a well-defined standard format. In summary, **no extra mapping configuration is typically needed** for NAXML 1.5 beyond selecting the correct format, but keep an eye out during testing.

## **4\. Validating Invoice Import and Checking Logs**

After configuration, you should confirm that the EDI import is functioning and be prepared to troubleshoot if any errors occur. Use the following steps to validate:

* **Initiate a Test Import:** Obtain a test NAXML invoice file from DABS if possible (perhaps ask them for a sample or use a recent actual invoice). Place this XML file into the configured EDI folder (`...edi\001\`) for your site. The CDB’s EDI service usually polls this directory regularly. Once the file is detected, the system will attempt to import it automatically. (If using the email-to-EDI service, send the file through that route and wait for it to drop into the folder.)

* **Monitor the Process:** In CDB’s interface, there may be an EDI **Import Log** or a status window that shows incoming EDI transactions. For example, SSCS’s Tip-of-the-Month (July) for EDI references a “summary of the EDI process as it relates to the CDB,” which likely includes checking a log on the SSCS Portal[m.facebook.com](https://m.facebook.com/photo/?fbid=551996286622064&set=ecnf.100054350928296#:~:text=Service%20,it%20relates%20to%20the%20CDB). In practice, many users simply check the **Direct Store Deliveries screen** – the new invoice should appear there once processed. Since SSCS advertises that an EDI invoice *“can be transmitted directly to the CDB”* when a vendor is set up[sscsinc.com](https://www.sscsinc.com/direct-store-deliveries/#:~:text=The%20process%20begins%20when%20the,the%20delivery%20to%20the%20CDB), a successful import means the invoice data now resides in your Daily Book records.

* **Confirm Invoice Entry:** Open the Purchases/Deliveries module in CDB and look for the DABS vendor. You should see a newly created invoice record corresponding to the file. It will include all the line items that were in the XML (quantity, item code, cost, etc.). Essentially, the system should have created the invoice **as if you entered it manually or scanned it**, but via the electronic file. This is the key benefit – “the invoice is transmitted directly” with no manual keying[sscsinc.com](https://www.sscsinc.com/direct-store-deliveries/#:~:text=The%20process%20begins%20when%20the,the%20delivery%20to%20the%20CDB).

* **Check for Errors:** If the invoice **does not appear**, or you get an error notification, then something went wrong. Common things to investigate:

  * **Log File:** On the CDB server, there might be a text-based log (e.g., `edi.log` or entries in an event log) that notes why the file was rejected. For example, an error might say “Unknown Vendor ID” or “XML parse error at line X”. Use any error details to pinpoint the issue.

  * **Vendor ID Mismatch:** The most frequent setup issue is the **vendor identifiers not aligning**. If the file’s vendor identifier (could be DUNS, or a SupplierNumber field in the XML) doesn’t match what CDB expects, the system won’t know this file is for DABS. Ensure the DUNS in the file matches 943556183 in your vendor record, or if the file uses another identifier (some NAXML files use a GLN or internal vendor code), that that value is present in the CDB config.

  * **Schema/Format Error:** If the file format is unexpectedly different, the parser might throw an error. Double-check you selected the correct format in the EDI setup. For instance, if by mistake the format was set to a different vendor’s layout, the fields might not line up. Selecting the generic NAXML (or “Conexxus XML”) format for invoices should avoid this.

  * **File Placement:** Verify the file was placed in the exact folder the system is monitoring. (It should be the `...edi\001\` folder for site 001 unless configured otherwise.) Also, ensure the file isn’t still in the folder – if an error occurred, sometimes the system leaves the file in place (or moves it to an “Error” subfolder). If it moved to **BAK without creating an invoice**, that implies the system thought it processed it – perhaps treat that as a clue to review the data in CDB (maybe it did import but under a different vendor or with missing data).

* **Review Alerts and Changes:** Assuming the invoice imported, CDB may flag certain things for your review:

  * **Price Changes:** The system will alert you if any item on the invoice has a cost that differs from your current record. SSCS notes that *“alerts when vendors change prices”* are a built-in benefit of the EDI process[sscsinc.com](https://www.sscsinc.com/direct-store-deliveries/#:~:text=There%20are%20many%20other%20benefits,our%20direct%20store%20delivery%20system). Check the **Outside Updates** or price change report – you may need to approve new costs so that your retail pricing can be adjusted accordingly.

  * **New Items:** If the DABS invoice contains items not yet in your item master, the system can flag these as **new item types delivered**[sscsinc.com](https://www.sscsinc.com/direct-store-deliveries/#:~:text=There%20are%20many%20other%20benefits,our%20direct%20store%20delivery%20system). Those will require you to add/confirm the new item in inventory (the system may create a placeholder record which you then complete). This is normal, as EDI can introduce new products; CDB gives you a chance to review them rather than automatically adding without your input.

* **Validate Data Integrity:** Open the imported DABS invoice in CDB and spot-check a few line items against the original XML or PDF invoice from DABS. Confirm fields like **invoice number**, **date**, **item UPC or code, quantities, unit costs, extended amounts, taxes/fees** (if any) all match. This will assure you that the NAXML mapping is correct (each XML element landed in the right database field). If anything looks off (e.g., every item has quantity zero, or prices seem wrong by a decimal place), that would hint at a mapping/version issue – which should be addressed before going live. In a correct setup, the electronic invoice in CDB will mirror the paper/email invoice exactly, line for line.

* **Logging of Process:** Keep a record of this test. If your system has a **batch log report**, print or save the log showing the successful import of the file (it might log a message like “Invoice 12345 from DABS imported successfully on \[date/time\]”). This log is useful for troubleshooting future issues and also serves as proof that the EDI flow is active.

## **5\. End-to-End Testing of the EDI Workflow**

Finally, run a full end-to-end test with all components involved, to ensure that when **real invoices arrive from DABS, everything works smoothly**:

* **Coordinate with DABS:** Inform DABS (or their IT team) that you are ready to test EDI. Ideally, schedule a time for them to send an **actual invoice** (or a test invoice) via their normal delivery method. This could be an email with the NAXML attachment or a file drop to a shared location, depending on how you’ve arranged to receive their files.

* **Email-to-EDI Flow (if used):** If DABS will email invoices, make sure the email is directed to the correct address. Many SSCS customers have an address like `<YourStore>@edidelivery.com` for such purposes[sscsinc.com](https://www.sscsinc.com/vendors/#:~:text=Vendor%20Details%20ABL%20Wholesale%20Distributors,mail%20address). Ensure any forwarding rules are in place so that the XML file gets into CDB’s EDI folder. *Example:* DABS might send to your regular email; you then forward it to the edidelivery address which auto-downloads into `Q:\cdbdata\edi\001\`. (If you’re not using the edidelivery service, you might simply save the attachment manually into the folder – just have a clear process so that when live invoices come, there’s no delay in getting the file into CDB.)

* **Receipt and Import:** When the test invoice is sent, monitor that it **appears in the CDB**. You should see, in real-time or within a few minutes, the invoice populate in the Direct Store Deliveries (DSD) or Purchases screen. Because the process is automated, this should happen without manual intervention: *“the invoice can be transmitted directly to the CDB”* once the vendor is set up for EDI[sscsinc.com](https://www.sscsinc.com/direct-store-deliveries/#:~:text=The%20process%20begins%20when%20the,the%20delivery%20to%20the%20CDB). This is your key indicator of success.

* **Invoice Reconciliation:** Treat the test invoice as you would a real delivery: check that the inventory was updated. The CDB now “knows” what you received from DABS on that invoice. You can run any standard **reports** (like a Received Items report) to ensure quantities and costs have been recorded. Also, verify that the invoice is now listed as **pending payment** in Accounts Payable with the correct totals (this confirms financial integration, if you use CDB for bookkeeping). The whole point of this setup is to seamlessly integrate DABS’s billing into your bookkeeping and inventory, which should now be happening.

* **Error Handling Check:** Induce or simulate an error scenario if possible to see how it’s flagged. For example, you might ask: *What if DABS sends an item that isn’t set up?* In your test, if a totally new item was on the invoice, CDB would put that in Outside Updates for you to confirm[sscsinc.com](https://www.sscsinc.com/direct-store-deliveries/#:~:text=There%20are%20many%20other%20benefits,our%20direct%20store%20delivery%20system) – check that you know how to handle that (you’d create the new item record or map it accordingly, then accept the update). Or *what if the file is malformed?* (You might not need to purposely break an XML, but know that if a file doesn’t import, it’s usually left in the folder or moved to BAK with no invoice created – and then you’d troubleshoot as in step 4.) Ensuring you’ve seen at least one failure in a controlled way can prepare you for real-world issues.

* **End-to-End Success:** A test is successful when: the DABS invoice file is received, **imported into CDB without errors**, and all data is correctly reflected in the system (inventory on-hand updated, vendor invoice available for review, price changes identified, etc.). You should be able to take the **physical paper** that arrived with the delivery (or a PDF of the invoice from DABS) and toss it aside, because all that information is now in CDB ready to be used. This significantly *“cuts delivery processing time… to a fraction of its previous length”* and ensures accuracy[sscsinc.com](https://www.sscsinc.com/direct-store-deliveries/#:~:text=There%20are%20many%20other%20benefits,our%20direct%20store%20delivery%20system).

## **6\. Additional Considerations and Best Practices**

* **Central Price Book (if used):** If you have a multi-store setup with Central Price Book (CPB), note that vendor imports interact with CPB’s zones. In CPB, you would configure *Vendor Import Setup* similarly (choosing the site directory, file mask, etc.) so that price updates flow into the CPB module[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=Import%20Type%20%E2%80%94%20Select%20the,combo%20box%2C%20select%20the%20site)[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=can%20have%20more%20than%20one,the%20vendor%20file%20to%20be). The general steps are the same, but you’d then use CPB’s *Outside Updates* to accept changes and *Distribute to Sites* to push data out[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=imported,Changes%20and%20additions%20in%20the)[portal.sscsinc.com](https://portal.sscsinc.com/wp-content/uploads/sites/3/documents/full_manuals/cpb40.pdf#:~:text=vendor%E2%80%99s%20pricing%20file%20are%20pushed,set%20up%20in%20the%20CDB). For a single-site CDB (no CPB), you can ignore this – the invoice goes straight into that store’s records.

* **Software Version:** Make sure your SSCS software is up-to-date. If you’re on a very old version of CDBWin, check the release notes for EDI improvements. The year 2023/2024 updates might have included minor tweaks for new vendors. Since DABS might be a newer integration, ensure you’re on a version that includes the latest *“approved EDI vendors”* list. (The SSCS website’s Approved EDI Vendors page is a good reference to see if new vendors require special handling – e.g., it notes some vendors that switched from email to other transfer methods, etc.[sscsinc.com](https://www.sscsinc.com/vendors/#:~:text=Vendor%20Details%20ABL%20Wholesale%20Distributors,mail%20transfer%20verified). Even if DABS isn’t listed, the fact that SSCS supports dozens of vendors means the infrastructure is robust.)

* **Training and Support:** If you haven’t already, consider reviewing SSCS’s training materials on EDI. They often have webinars or videos on “Direct Store Deliveries via EDI” and how to troubleshoot them. The **SSCS Support team** can also verify your setup if you open a ticket – since this is a critical vendor (state-controlled alcohol), they understand the importance of getting it right.
