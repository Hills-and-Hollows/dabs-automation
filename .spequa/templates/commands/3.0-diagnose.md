## Pipeline Position

```
⭐ DIAGNOSE → clarify → plan → tasks → analyze → test → implement → PR → merge → close
```

This command is an **alternative entry point** to the pipeline for bug-fix-driven development. It replaces `/spequa.3-spequafy` when the work is driven by a bug report rather than a new feature request. The output is a `spec.md` file with a `**Type**: Bug Fix` marker and prepended Problem Definition + Root Cause Analysis sections that feed into the existing downstream pipeline (plan, tasks, implement) without modification.

Also accessible via `/spequa.3-spequafy --bugfix`.

## Outline

### Phase 1: Problem Definition

**Goal**: Document the bug with enough structure to enable reproducibility and root cause investigation.

1. Parse the user's bug description from `$ARGUMENTS`. If empty: prompt the user to describe the bug.

2. **Guided Problem Documentation** — walk the user through each section:

   **a. Observed Behavior**:
   - Ask: "What is actually happening? Be specific — include error messages, incorrect output, or unexpected behavior."
   - If the user's description is clear, extract it directly. If vague, ask one follow-up.

   **b. Expected Behavior**:
   - Ask: "What should happen instead?"
   - If inferable from the observed behavior (e.g., "crashes" → "should not crash"), auto-fill and confirm.

   **c. Reproduction Steps**:
   - Ask: "What steps reproduce this bug? Number them sequentially."
   - If the user can't reproduce reliably, document as: "Intermittent — observed under [conditions]."
   - **Codebase Investigation**: Scan the codebase for the affected code path. Read relevant source files to understand the flow. Include file paths in the reproduction context.

   **d. Affected Components**:
   - Auto-detect from reproduction steps and codebase investigation. List specific file paths or module names.
   - Ask user to confirm or add components.

   **e. Severity Assessment**:
   - Present severity options:

   | Severity | Criteria |
   |----------|----------|
   | Critical | Data loss, security breach, complete feature unavailable |
   | High | Major feature broken, no workaround |
   | Medium | Feature partially broken, workaround exists |
   | Low | Minor inconvenience, cosmetic, edge case |

   - Recommend a severity based on the observed behavior. User confirms or overrides.

   **f. Environment** (optional):
   - Ask: "Is this environment-specific? (OS, version, configuration)"
   - If the user says no or it's not relevant, omit this section.

3. **Write Phase 1 to spec.md**: Write the completed Problem Definition to `SPEC_FILE` immediately after completion. Include the file metadata header:

   ```markdown
   # Feature Specification: [Fix: Brief Description]

   **Feature Branch**: `[BRANCH_NAME]`
   **Created**: [DATE]
   **Status**: Draft
   **Input**: Bug report: "[original bug description]"
   **Type**: Bug Fix

   ## Problem Definition

   [completed sections]
   ```

4. **Save immediately** — atomic write to `SPEC_FILE` so the phase persists for pause/resume.

5. Report: "Phase 1 complete — Problem Definition documented. Proceeding to Root Cause Analysis."

---

### Phase 2: Root Cause Analysis

**Goal**: Investigate candidate causes, gather evidence, and confirm the root cause.

1. **Load context**: Read the Problem Definition from `SPEC_FILE`. Read the affected components source files.

2. **Codebase Investigation**:
   - Read each file listed in Affected Components
   - Trace the code path described in Reproduction Steps
   - Look for: error handling gaps, incorrect logic, race conditions, missing validation, type mismatches, stale state

3. **Generate Candidate Causes**:
   - Based on the codebase investigation, identify 2-5 candidate root causes
   - For each candidate, document:
     - **Description**: What might be causing the bug
     - **Evidence for**: Code observations, log patterns, or test results that support this hypothesis
     - **Evidence against**: Observations that contradict this hypothesis

4. **Present Candidates to User**:
   - Show all candidates with their evidence
   - Recommend the most likely candidate based on evidence weight
   - Ask: "Which root cause do you believe is correct? Or should we investigate further?"

5. **Confirm Root Cause**:
   - Record the user's selection (or the recommended cause if user accepts)
   - Set confidence level:
     - **Confirmed**: Root cause verified by code reading / reproduction / test
     - **Likely**: Strong evidence but not definitively proven
     - **Uncertain**: Best hypothesis available but needs further investigation

6. **Write Phase 2 to spec.md**: Append the Root Cause Analysis section to `SPEC_FILE`, after the Problem Definition section:

   ```markdown
   ---

   ## Root Cause Analysis

   ### Candidate Causes
   [all candidates with evidence]

   ### Confirmed Root Cause
   [selected cause]

   **Confidence**: [level]
   ```

7. **Save immediately** — atomic write.

8. Report: "Phase 2 complete — Root Cause identified. Proceeding to Fix Specification."

---

### Phase 3: Fix Specification

**Goal**: Generate a standard spec (User Scenarios, Requirements, Success Criteria) scoped to the targeted fix, compatible with downstream pipeline steps.

1. **Load context**: Read both Problem Definition and Root Cause Analysis from `SPEC_FILE`.

2. **Generate Fix Specification** using the standard spec template structure:

   **a. User Scenarios & Testing**:
   - P1 story: The direct fix — describe the corrected behavior
   - P2 story (if applicable): Related edge cases exposed by the root cause
   - Each story MUST include regression test criteria
   - Edge cases: boundary conditions related to the bug

   **b. Functional Requirements**:
   - FR for the corrected behavior ("System MUST...")
   - FR for the eliminated bug behavior ("System MUST NOT...")
   - FR for regression protection ("System MUST continue to...")
   - Scope requirements tightly to the fix — do not expand into feature work

   **c. Success Criteria**:
   - SC-001: Bug no longer reproduces under documented reproduction steps
   - SC-002: Existing functionality in affected area continues to work (regression)
   - Additional SCs based on the root cause and fix scope

3. **Write Phase 3 to spec.md**: Append the fix specification sections to `SPEC_FILE`, after the Root Cause Analysis section. The final file structure matches the contract in `contracts/diagnose-artifact-format.md`.

4. **Specification Quality Validation**: Run the same quality checks as `/spequa.3-spequafy`:
   - Create `FEATURE_DIR/checklists/requirements.md`
   - Validate completeness, clarity, measurability
   - Max 3 `[NEEDS CLARIFICATION]` markers (resolve inline if possible)

5. **Save immediately** — atomic write.

6. Report completion:
   - Path to completed `spec.md`
   - Checklist results
   - Suggest next step: `/spequa.4-clarify` (if clarifications remain) or `/spequa.5-plan`

## Anti-Patterns — What This Command Does NOT Do

- ❌ Does NOT implement the fix — that's `/spequa.10-implement`
- ❌ Does NOT modify the existing `/spequa.5-plan`, `/spequa.6-tasks`, or `/spequa.10-implement` workflows — the fix spec is compatible with them as-is
- ❌ Does NOT assign blame or identify who introduced the bug
- ❌ Does NOT create tests — that's `/spequa.9-test`
- ❌ Does NOT auto-fix the code — it produces a structured specification for the fix

## Behavior Rules

- **Investigate before assuming**: ALWAYS read affected source code before generating candidate causes. Do not guess root causes without evidence.
- **Scope tightly**: Fix specifications should address ONLY the reported bug and directly related edge cases. Feature expansion is a separate spec.
- **Save after each phase**: Each phase writes to `SPEC_FILE` immediately to enable pause/resume.
- **Detect resume state**: Always check for existing section headings before starting a phase.
- **Severity is informational**: The same workflow runs for all severity levels. Severity does not gate any steps.
- **Confidence is honest**: Use "Uncertain" when the root cause cannot be definitively confirmed through code reading alone.
- **Downstream compatibility**: The output `spec.md` must be accepted by `/spequa.5-plan` without modification. Test this by verifying the file contains `## User Scenarios & Testing`, `## Requirements`, and `## Success Criteria` sections.
